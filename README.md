# AttendanceControl

**Проект:** «Система контроля посещаемости студентов»  
**Платформа:** Android  
**Язык:** Kotlin

---

## 1. Назначение проекта

AttendanceControl — Android-приложение для ведения списка студентов, фиксации посещаемости занятий и просмотра статистики.

Приложение предназначено для работы на одном Android-устройстве. Данные сохраняются локально в базе SQLite через Room. Серверная часть, облачная синхронизация и обмен данными между устройствами не реализованы.

В проекте предусмотрен демонстрационный вход с двумя тестовыми ролями: учитель и администратор.

## 2. Возможности приложения

- Демонстрационная авторизация с автоматическим определением роли по логину и паролю.
- Главное меню с переходами к разделам приложения.
- Просмотр списка студентов с группировкой по учебным группам.
- Добавление и удаление студентов администратором.
- Просмотр списка студентов учителем без формы управления.
- Отметка каждого студента как присутствовавшего, отсутствовавшего или опоздавшего.
- Сохранение дисциплины, даты занятия и статусов посещаемости.
- Просмотр сводной статистики и истории посещаемости.
- Фильтрация статистики по группе и статусу.
- Выход из аккаунта с возвратом на экран авторизации.

## 3. Тестовые учётные записи

| Роль | Логин | Пароль |
|---|---|---|
| Учитель | `teacher` | `teacher123` |
| Администратор | `admin` | `admin123` |

Роль определяется автоматически по введённой паре логин/пароль. Отдельного переключателя роли на экране входа нет.

**Важно:** это демонстрационная локальная авторизация. Учётные данные зашиты в клиентское приложение, не проверяются сервером и не обеспечивают настоящую защиту. Не используйте эти учётные записи для реальных пользователей или конфиденциальных данных.

Разграничение прав реализовано частично: на экране студентов администратор может добавлять и удалять записи, а учитель — только просматривать список. Остальные разделы не имеют полноценной проверки прав на уровне защищённого сервера.

## 5. Запуск проекта

1. Установить Android Studio с поддержкой используемой версии Android Gradle Plugin и SDK.
2. Клонировать репозиторий и открыть корневую папку проекта в Android Studio.
3. Дождаться синхронизации Gradle. При необходимости установить Android SDK Platform 37.
4. Выбрать конфигурацию запуска `app`.
5. Запустить приложение на эмуляторе или физическом устройстве с Android 7.0 (API 24) или новее.

Команды Gradle из корня проекта:

```bash
# Сборка debug-варианта
./gradlew :app:assembleDebug

# Unit-тесты
./gradlew :app:testDebugUnitTest

# Инструментальные тесты (нужен подключённый эмулятор или устройство)
./gradlew :app:connectedDebugAndroidTest
```

В Windows вместо `./gradlew` используется `gradlew.bat`.

## 6. Экраны приложения

| Экран | Kotlin-класс | XML-разметка | Назначение |
|---|---|---|---|
| Авторизация | `LoginActivity` | `activity_login.xml` | Проверяет тестовые учётные данные и определяет роль |
| Главное меню | `MainActivity` | `activity_main.xml` | Навигация по разделам и выход из аккаунта |
| Студенты | `StudentsActivity` | `activity_students.xml` | Просмотр списка; добавление и удаление для администратора |
| Отметка посещаемости | `AttendanceActivity` | `activity_attendance.xml` | Выбор дисциплины, даты и статуса для каждого студента |
| Статистика | `StatisticsActivity` | `activity_statistics.xml` | Сводные показатели, фильтры и история записей |

Переходы между экранами выполняются через Android `Intent`. Роль пользователя передаётся из `LoginActivity` в `MainActivity`, а затем в `StudentsActivity`.

## 7. Работа с посещаемостью

Перед сохранением отметок приложение проверяет:

- заполнены ли дисциплина и дата;
- соответствует ли дата формату `ГГГГ-ММ-ДД` и является ли календарно корректной;
- выбран ли статус для каждого загруженного студента.

Варианты статуса:
- `Присутствовал`
- `Отсутствовал`
- `Опоздал`

Для каждого студента создаётся отдельная запись посещаемости. Повторное сохранение тех же студента, даты и дисциплины добавит новую запись: уникальное ограничение для такой комбинации и логика обновления существующей отметки не реализованы.

## 8. Статистика

Экран статистики получает данные через `AttendanceDao` и отображает количество записей по трём статусам, процент посещаемости и историю.

Формула процента посещаемости:

```text
(количество «Присутствовал» + количество «Опоздал»)
--------------------------------------------------- × 100
                 общее количество отметок
```

Если записей нет, процент равен 0.

Доступны фильтры:
- по группе;
- по статусу.

Фильтрация выполняется в приложении по загруженному списку. После применения фильтров список сортируется по дате по убыванию и ограничивается 100 записями. Сводные карточки пересчитываются по отфильтрованному списку. Счётчик показывает количество отображаемых записей относительно общего количества загруженных записей.

## 9. Структура базы данных

База Room называется `attendance_database`. Она содержит две сущности.

### Таблица `students` — студенты

| Поле | Тип | Описание |
|---|---|---|
| `id` | Int, Primary Key | Автоматически создаваемый идентификатор |
| `firstName` | String | Имя |
| `lastName` | String | Фамилия |
| `groupName` | String | Название или номер группы |

### Таблица `attendance` — посещаемость

| Поле | Тип | Описание |
|---|---|---|
| `id` | Int, Primary Key | Автоматически создаваемый идентификатор записи |
| `studentId` | Int | Идентификатор студента, к которому относится отметка |
| `lessonDate` | String | Дата занятия в формате ГГГГ-ММ-ДД |
| `subject` | String | Дисциплина или тема |
| `status` | String | Статус посещаемости |

Поле `studentId` используется для связывания отметки со студентом в SQL-запросе `JOIN`. В текущем описании Entity нет объявленного Room foreign key constraint, поэтому не следует считать, что база автоматически обеспечивает ссылочную целостность или каскадное удаление.

### Основные компоненты Room

- `StudentEntity`, `AttendanceEntity` — описывают строки таблиц.
- `StudentDao` — добавляет, получает и удаляет студентов.
- `AttendanceDao` — сохраняет отметки, получает историю, считает статусы и соединяет отметки с данными студентов.
- `AppDatabase` — конфигурация Room и Singleton-доступ к базе.
- `StatusCount` — результат агрегирующего запроса: статус и количество.
- `AttendanceWithStudent` — результат JOIN-запроса с ФИО и группой студента.

**Особенность миграций:** база имеет версию 1 и настроена с `fallbackToDestructiveMigration(dropAllTables = true)`. При изменении версии схемы без подходящей миграции таблицы могут быть пересозданы, а локальные данные — потеряны.

## 10. Архитектура и взаимодействие компонентов

Проект разделён на UI, данные и вспомогательные функции. Это простое разделение ответственности, но не полноценная реализация MVVM: отдельные слои Repository и ViewModel в текущем коде не используются.

Типичный поток сохранения посещаемости:

1. Пользователь работает с `AttendanceActivity`.
2. `AttendanceAdapter` отображает студентов и хранит выбранные статусы.
3. `AttendanceActivity` проверяет введённые данные и формирует объекты `AttendanceEntity`.
4. `AttendanceDao` вставляет список записей.
5. Room сохраняет данные в SQLite.
6. `StatisticsActivity` читает записи через DAO, применяет фильтры и передаёт результат в `HistoryAdapter`.

`lifecycleScope.launch` используется для запуска suspend-операций DAO в корутинах, связанных с жизненным циклом Activity.

## 12. Тестирование

В репозитории предусмотрены два вида тестов:

### Unit-тесты — `app/src/test/`

Проверяют отдельную логику, в частности валидацию данных студента: корректные значения, пустые строки и строки из пробелов.

Запуск:

```bash
./gradlew :app:testDebugUnitTest
```

### Инструментальные тесты — `app/src/androidTest/`

Запускаются на Android-устройстве или эмуляторе. Для тестирования базы используется Room in-memory. Тесты охватывают запросы статистики и истории, пустые результаты, наборы записей и сценарии UI.

Запуск:

```bash
./gradlew :app:connectedDebugAndroidTest
```

Статусы тестов, указанные в прежних отчётах проекта, не являются подтверждением того, что тесты были запущены на текущем коммите. Перед релизом следует выполнить команды тестирования на актуальной версии кода.

## 13. Известные ограничения и дальнейшая работа

- Авторизация демонстрационная; для реального применения нужна серверная аутентификация и безопасное хранение учётных данных.
- Роли разграничивают возможности на экране студентов, но не образуют полноценную систему разрешений.
- Нет серверной синхронизации, резервного обмена данными между устройствами и многопользовательского режима.
- Повторное сохранение отметки создаёт новую запись, а не обновляет существующую.
- Для `attendance.studentId` не объявлен Room foreign key constraint; удаление студента не выполняет каскадное удаление его отметок. Запрос истории статистики использует INNER JOIN, поэтому записи без соответствующего студента не попадут в этот результат.
- При destructive migration возможна потеря локальных данных.
- Фильтры статистики применяются на клиенте, а отображаемая история ограничена 100 записями.
- В Gradle-конфигурации есть дублирующая декларация Room KTX с разными версиями; её стоит привести к единой версии.
